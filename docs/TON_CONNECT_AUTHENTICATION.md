# V COIN – TON Connect Wallet Authentication

**Implementation action:** 54  
**Status:** Backend proof verification and wallet binding implemented; automated verification in progress.  
**Mining status:** Public mining remains disabled. Wallet authentication alone does not authorize rewards or payouts.

## Security model

- A user must first authenticate through the existing Telegram backend session.
- The proof challenge is generated by the backend using 32 cryptographically random bytes.
- The challenge is stored only as a SHA-256 hash and is bound to the authenticated user, exact backend session, and selected TON network.
- Challenges expire after 10 minutes and are consumed atomically once.
- The backend checks the connected address against the address derived from the supplied wallet StateInit.
- The public key is extracted only from reviewed standard TON wallet contract code versions (V1R1–V5R1); the wallet-reported public key, when present, must match.
- Ed25519 signature, dApp domain, UTF-8 domain byte length, timestamp, network global ID, and challenge are validated.
- Verified Mainnet and Testnet wallets are stored independently using their TON global IDs (`-239` and `-3`).
- Unsupported wallet contracts, malformed proofs, stale proofs, and replayed challenges are rejected. WalletTg and non-standard wallet implementations are not enabled by this allowlist.
- No seed phrase, private key, wallet PIN, or signing key is requested or stored.

## Configuration

Set the exact hostname used by the TON Connect manifest in the backend environment:

```env
TON_PROOF_DOMAIN=app.example.com
```

Do not include a scheme, path, or trailing slash. Leave the setting unset until the final staging/production hostname is selected; proof verification then fails closed with HTTP 503.

## Authenticated API

Both endpoints require the existing Telegram session:

```http
Authorization: Bearer <access_token>
Content-Type: application/json
```

### 1. Request a challenge

`POST /api/v1/wallet/ton-proof/payload`

Request:

```json
{ "network": "-239" }
```

Use `"-239"` for Mainnet or `"-3"` for Testnet.

Response:

```json
{ "payload": "<random-single-use-challenge>", "expiresIn": 600 }
```

Pass the returned value as the TON Connect `tonProof` payload before opening the wallet connection request.

### 2. Verify and bind the wallet

`POST /api/v1/wallet/ton-proof/verify`

Request:

```json
{
  "address": "<TonConnect account address>",
  "network": "-239",
  "publicKey": "<optional 64-character hex public key>",
  "walletStateInit": "<base64 StateInit BOC>",
  "proof": {
    "timestamp": 1795420800,
    "domain": { "lengthBytes": 15, "value": "app.example.com" },
    "signature": "<base64 Ed25519 signature>",
    "payload": "<the exact backend-issued challenge>"
  }
}
```

The endpoint also accepts the TON Connect wire representation with `proof.state_init` instead of top-level `walletStateInit`.

Successful response:

```json
{
  "walletAddress": "<raw TON address>",
  "network": "mainnet",
  "walletVerified": true
}
```

A verified wallet is bound to the current account and chain. A different verified wallet cannot silently replace it. Mainnet and Testnet bindings are separate records.

## Explicitly not enabled

This work does not yet:
- Read a live VCOIN Jetton balance from a configured TON RPC provider.
- Persist a chain-verified balance snapshot for mining accrual.
- Enable public mining routes or payouts.
- Submit any Mainnet or Testnet transaction.

Those remain separate release gates.
